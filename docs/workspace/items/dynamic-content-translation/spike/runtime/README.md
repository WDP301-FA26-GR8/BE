# Spike: runtime and lifecycle of the translation engine

Status: spike code and measurements, 14/10/2026, revised 15/10/2026 after review (section 6), written by an AI implementer (Sonnet 5.5). Not product code, not reviewed by a dev.
Sections 1 to 5 describe the 14/10 state; where the review round changed a statement it is corrected in place and marked (15/10). Section 6 lists every change, the V-3/V-4 dispositions and the round-2 results.
Nothing here modifies the BE product. Plain ESM (`.mjs`), no TypeScript, no product imports, only Node built-ins in the supervisor side.
Measurements are from one machine (Windows 11 host, Docker Desktop, WSL2 kernel 6.6.87) that other jobs also used while the benches ran; see "Limitations".

### Design summary

- **Topology.** The API process never imports transformers. `Supervisor` forks up to `concurrency` (default 1) worker processes with an explicit minimal env (`SPIKE_MODELS_DIR`, `SPIKE_INTRA_THREADS`, `NODE_ENV`, optional `SPIKE_DEPS_DIR`, plus `PATH` and, on Windows, `SystemRoot`; no secrets, parent env not inherited), `execArgv: ['--max-old-space-size=256']`, piped stdio (drained, never forwarded). The worker exits on `disconnect`. One job at a time per worker.
- **IPC.** supervisor to worker: `load{direction}`, `run{jobId,direction,segments,computeDeadlineEpochMs,maxNewTokensRule}`, `cancel{jobId}`, `unload{direction}`, `shutdown`. worker to supervisor: `loaded{direction,ms,rssMb}`, `loadFailed{direction,permanent}`, `started`, `done{jobId,outputs,complete,deadlineHit,cancelled,stats}`, `error{jobId,code}`, `unloaded`. Raw text and library error messages never travel back; errors map to codes (`RUN_FAILED`, `NOT_LOADED`, `CRITERION_NOT_INVOKED`).
- **Model states** (per worker, per direction): UNLOADED, LOADING, READY, DISPOSING, UNLOADED; FAILED is tracked per direction: permanent, or transient with backoff 1 s doubling to 60 s (inside the window jobs fail fast with `LOAD_BACKOFF`, nothing is spawned). `loadTimeoutMs` (30 s) kills a stuck loader; the job fails `LOAD_TIMEOUT` and counts as a transient load failure.
- **Job states:** QUEUED, RUNNING, (CANCEL_REQUESTED), DONE | ABANDONED | FAILED. QUEUED becomes ABANDONED (`REMOVED_QUEUED`) when waiters reach 0. A complete result that races with a cancel is still DONE (so it can be cached).
- **Slot rule.** A slot is released only on `done`/`error` from that worker, when a cancelled job's blocking model load answered (no run is started), on that worker's `exit` event (crash or our SIGKILL), or (15/10, V-3) when NO process exists: a synchronous `spawn` throw or an async `'error'` with `pid` undefined before `'spawn'`. A lost `exit` event is covered by a bounded wait that consults the child's own fields (section 6). Never on caller timeout, abort, compute deadline or any timer. A new process is spawned only after the previous process's `exit`. `bench/analyze.mjs` re-checks all of this from the event log.
- **Three clocks plus the load budget (15/10).** (1) `responseDeadline` per waiter, `min(arrival + timeoutMs (10 s), deadlineAt)`, includes queue and cold load, settles that waiter alone with `TIMEOUT`. (2) `computeDeadline` per job = the moment `run` is SENT to a worker that is READY for the direction + `computeMaxMs` (10 s), enforced cooperatively inside the worker by the stopping criterion (the supervisor also sends `cancel` unless `deadlineCancel:false`). 14/10 started this clock at dispatch; see V-4 in section 6. (3) kill timer = computeDeadline + `killGraceMs` (3 s); SIGKILL, then ABANDONED only after the child `exit`. (4) `loadTimeoutMs` (30 s) bounds spawn + model load.
- **Single-flight.** `inflight` holds only QUEUED/RUNNING jobs; same-key callers join without using queue slots; every waiter has its own timer and AbortSignal listener and a settle-once guard; one waiter leaving never cancels the others; at 0 waiters QUEUED is removed and RUNNING is cancelled (and leaves `inflight`, so a new caller gets a fresh job). `queueMax` (4) full means immediate `BUSY`. `maxInflightObserved` is tracked and asserted `<= queueMax + concurrency`.
- **Late results.** A complete result arriving after all waiters left is cached; settled waiters are no longer attached to the job, so it is never delivered to them.
- **Cache.** Supervisor process only. LRU bounded by 500 entries and 8 MiB (approx `(key.length + value.length) * 2`), TTL 86400 s lazy expiry. Key = HMAC-SHA256 under `crypto.randomBytes(32)` per process over `JSON.stringify(["tr-v1", org, scope, engineId, modelDigest, glossaryVersion, "nfc-ws-v1", placeholderPolicyVersion, source, target, sha256(normalizedText)])`. Only complete successes are stored; no negative caching. No list/delete/peek API exists.
- **Circuit breaker** (per direction): 3 failures (deadline hit, kill, crash, transient load failure) in 5 min open it; cooldown 30 s doubling to 5 min on probe failure; HALF_OPEN admits exactly one probe; a permanent load failure makes that direction permanently UNAVAILABLE.
- **Shutdown:** stop admission, settle queued waiters `UNAVAILABLE`, cancel running, wait for `done` up to `shutdownGraceMs` (5 s), send `shutdown` (worker disposes pipelines, exit 0), SIGKILL on grace expiry, resolve after every exit.
- **Coordinator contract.** (15/10) `translate({organizationId, scope, text, storedSource, sourceOverride?, target, signal, deadlineAt})` returns `{status: 'OK'|'TIMEOUT'|'UNAVAILABLE'|'BUSY', text, cacheHit, stats, sourceLanguage, effectiveSourceLanguage, sourceOverridden, textLanguage}` (14/10 had `source` instead of `storedSource`; it is still accepted as an alias). The caller MUST authorize access to the text before calling. On any non-OK status `text` is `null` and the product caller returns the original text (that mapping is the product's job). `stats.reason` is a short machine code.

### Generation path (transformers.js 4.3.1 regression)

transformers.js 4.3.1 no longer maps the textual `>>vie<<` prefix to the single vocab id 3 (it is split into 5 sub-tokens and en to vi quality collapses; coordinator finding, see `spike/deps/probe-prefix-workaround.mjs`). The worker therefore uses a **direct-generate path for both directions**: tokenize each sentence without any prefix, prepend the language-token id looked up from the vocab for en to vi (`tokenizer.get_vocab()` in 4.x, `tokenizer.model.tokens_to_ids` in 3.x), then `pipe.model.generate({input_ids, attention_mask, max_new_tokens, stopping_criteria: [criterion]})` and `tokenizer.batch_decode(..., {skip_special_tokens: true})`. A startup self-test per direction (vocab has the token, first id is 3, fixed sentence tokenizes to at least 5 ids) fails `loadFailed{permanent:true}`. Segments are translated **one at a time** (batch size 1): padded batches were reported to add trailing `!` (not re-measured here; I did not measure batching). On this path every number below was produced; the fake-worker tests are path independent. Real en to vi output with this path is identical on 4.3.1 and 3.8.1 for the two test sentences (`Giấy phép sẽ hết hạn vào cuối tháng này.` for `The license will expire at the end of this month.`).

### Decisions and deviations to review

1. After a `cancel` while the job is EXECUTING, the kill timer is re-armed to `cancel + killGraceMs` (not only computeDeadline + grace), so a native hang after a caller left does not hold the slot for 13 s. During a blocking model load the kill timer is not re-armed (load is awaited).
2. (15/10, superseded) 14/10 had the compute window include spawn and cold model load; reviewers found it consumes the budget after every crash or cold start. Decided: the compute clock starts when `run` is sent to a READY worker; the load has its own `loadTimeoutMs`; each waiter's response deadline still bounds the total. See V-4 in section 6.
3. The supervisor also sends `cancel` at the compute deadline (belt and braces) unless `deadlineCancel:false`. With it on, the worker usually reports `cancelled` and the supervisor maps it to DEADLINE; the overrun numbers below were measured with it off, so the worker's own criterion is the only enforcer.
4. Breakers are per direction (a bad model for one direction must not block the other). Cache hits are served before the breaker check, also while OPEN.
5. Empty/whitespace text returns `OK` with the text unchanged and never reaches a worker; unsupported pair returns `UNAVAILABLE`.
6. `loadTimeoutMs` also covers node process boot (the `load` request is queued on IPC from spawn); it was flaky-small in a test under parallel CPU load, hence 800 ms in that test.
7. Not implemented: worker-process event-loop delay, glossary/placeholder logic, wiring into NestJS. (15/10: the integrity gate now exists, `verify-lock.mjs`; the bench `modelDigest` for the cache key is still only an identity.)

## 2. How to run

Prerequisites: Node 24, Docker Desktop (image `node:24-bookworm-slim`), models mounted read-only from `.models/translation`. Nothing is installed in the repo.

Install (record of what was used). pnpm 11.1.3 (`npx pnpm@11.1.3`), `@huggingface/transformers@4.3.1`, `--ignore-scripts`, `pnpm-workspace.yaml` has `allowBuilds` all false and `overrides: '@huggingface/transformers>onnxruntime-web': '-'` (`install/`). Resolved: onnxruntime-node 1.30.0, sharp 0.35.5, no onnxruntime-web.

```bash
# Linux (primary): from Git Bash on Windows or any bash with docker, in spike/runtime
# (15/10) ownership rules: see 6.7. install never overwrites; test/bench need SPIKE_DEPS_VOLUME explicitly.
./run-linux.sh install                      # phase 1, network on, NEW volume spike-rt-deps-<RUN_ID> (or: install --reuse spike-runtime-deps)
export SPIKE_DEPS_VOLUME=spike-runtime-deps
./run-linux.sh test                         # node --test incl. real-model tests, offline container
./run-linux.sh bench env coldload healthcompare saturation overrun killexit extkill killcycles threads sigterm clock spawnfail
BENCH_JOBS=1000 ./run-linux.sh bench longrun
./run-linux.sh bench latency                # BENCH_LAT_CONC=1,2 BENCH_LAT_DIRS=vi-en,en-vi (defaults)
# containers: --network none, user node, --cpus=2 --memory=2g --memory-swap=2g, models and spike dir :ro, one container per scenario

# Windows / any host (needs a deps dir containing node_modules/@huggingface/transformers)
cd spike/runtime
node --test "test/*.test.mjs"                                    # fake-worker tests, real tests skipped
SPIKE_REAL=1 SPIKE_DEPS_DIR=<deps> SPIKE_MODELS_DIR=<models> node --test "test/*.test.mjs"
SPIKE_DEPS_DIR=<deps> SPIKE_MODELS_DIR=<models> BENCH_OUT=./evidence BENCH_PROFILE=win32 BENCH_FAST=1 node bench/run.mjs coldload ...
```

Env: `SPIKE_DEPS_DIR` (dir with `node_modules/@huggingface/transformers`; point it at a 3.8.1 install to compare, tested with 3.8.1: real tests 5/5), `SPIKE_MODELS_DIR`, `SPIKE_REAL=1`, `SPIKE_INTRA_THREADS`, `BENCH_OUT`, `BENCH_PROFILE`, `BENCH_FAST=1`, `BENCH_JOBS`, `BENCH_LAT_CONC`, `BENCH_LAT_DIRS`, `BENCH_INTRA`; API-side `BENCH_CONCURRENCY`, `BENCH_QUEUE_MAX`, `BENCH_COMPUTE_MAX_MS`, `BENCH_KILL_GRACE_MS`, `BENCH_TIMEOUT_MS`, `BENCH_BREAKER_THRESHOLD`, `BENCH_SHUTDOWN_GRACE_MS`, `BENCH_DEADLINE_CANCEL=0`, `BENCH_MODE=inproc`.

### Other measured facts

- `healthcompare` saturation (10 clients, 30 requests of 400 chars, one worker, queue large): worker mode request latency p50 34.9 s (run B) / similar, because one worker serialises about 2.4 s jobs; in-process p50 38 s. Throughput is the same; the difference is the loop: see item 2/3.
- Saturation scenario outcome: the 10 kills landed while EXECUTING (10/10); 15 deadline failures and 10 crash failures were counted by the supervisor; 2 `killed` outcomes were supervisor SIGKILLs (reason `unresponsive`); my reading is that they were cold loads still running at deadline + grace (200 ms + 3 s) under contention, but I did not record the phase, so this is UNVERIFIED.
- `inflightMaxObserved` 5 = `queueMax + concurrency`, never above the bound.
- The in-process baseline translates the same way (direct generate) without a deadline; it shows the design's reason, not a competing recommendation.

### 6.1 V-3 spawn failure and ChildProcess `'error'`

Node docs (child_process, `'error'` event): "The `'error'` event is emitted whenever: the process could not be spawned; the process could not be killed; sending a message to the child process failed; the child process was aborted via the `signal` option. The `'exit'` event may or may not fire after an error has occurred." `subprocess.pid`: "If the child process fails to spawn due to errors, then the value is `undefined` and `error` is emitted." `'spawn'`: "emitted once the child process has spawned successfully ... If the child process does not spawn successfully, the `'spawn'` event is not emitted and the `'error'` event is emitted instead." `subprocess.kill()` "returns `true` if kill(2) succeeds, and `false` otherwise" and may emit `'error'` if the signal cannot be delivered; `exitCode` / `signalCode` are `null` while the child runs.

Disposition (fixed, `supervisor.mjs`, `test/supervisor-spawn.test.mjs` 11 tests on an in-memory `FakeChild`):

| Situation                                                                        | Rule                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `spawnFn` throws synchronously                                                   | no child exists: slot released, job settled once `FAILED/SPAWN_FAILED`, `failure{kind:'spawnFailed'}` (breaker counts it), queue continues. The raw error message is never copied (only a short code in the `spawnFailed` event).                                                                                                                                                           |
| `'error'` with `pid === undefined` and no `'spawn'` event yet                    | same as above (async variant); a late `'exit'` of that phantom child is ignored by the `slot.child !== child` guard. The event log has `spawn` then `spawnFailed{phase:'async'}`; `bench/analyze.mjs` treats that pair like spawn/exit.                                                                                                                                                     |
| `'error'` on a live child (pid defined or `'spawn'` seen: IPC error, kill error) | the slot is NOT released. The child is killed through the handle the supervisor owns (`SIGKILL`) and the supervisor waits for `'exit'`; the job then settles `FAILED/CHILD_ERROR` (counted as `crash`), next spawn only after the exit.                                                                                                                                                     |
| `kill()` throws or returns false, or `'exit'` never arrives                      | every kill arms an exit-wait bound (`exitWaitMs`, default 2 s). On expiry the slot is marked dead (synthetic exit, flagged `synthetic:true` in the event) ONLY IF `child.exitCode !== null \|\| child.signalCode !== null \|\| child.pid === undefined`; otherwise the process is treated as alive: SIGKILL again, wait again, slot stays held, so live processes never exceed concurrency. |

Tests cover: sync throw (single and 4 queued jobs), async error with no exit, async error then late exit, live-child error then exit (no respawn before exit, killed by own handle), kill throwing with fields still "running" (slot held, kill retried, then released when the fields show dead), kill returning false with `exitCode` set, a throwing kill on the unresponsive-worker path, a mixed concurrency-2 run (max live <= 2, from OS-like liveness, from events, and from the offline checker), shutdown with a failed spawn and with an IPC error, settle exactly once. Limit: a process that is genuinely alive and unkillable keeps its slot forever and blocks `shutdown()`; that is the safe side and is reported by the `exitWaitExpired` event.

### 6.2 V-4 compute clock

Decision implemented: `computeDeadline = (moment run is SENT to a worker READY for the direction) + computeMaxMs`; the kill timer is `computeDeadline + killGraceMs` (or cancel + grace). Spawn and model load are bounded by `loadTimeoutMs`; every waiter's response deadline (arrival + `timeoutMs`) still bounds the total, so nothing is unbounded. New event `runSent{computeDeadlineEpochMs}`. `test/clock.test.mjs` (9 tests): a 700 ms cold load with `computeMaxMs` 250 completes; the deadline and kill timer are measured from run-sent (deadline event 140 to 300 ms after run-sent but 540+ ms after dispatch); no deadline or kill fires during a load and a cancel during load is `CANCELLED`; `loadTimeoutMs` still kills a stuck loader; the warm path is unchanged (run-sent < 25 ms after dispatch); coordinator: cold load OK, waiter timeout during a long load (job cancelled, no run sent, model kept, next call warm with one load), queue timeout during a cold load.

### 6.3 Truncation

`worker/run-job.mjs` + the adapter (`spike/quality/lib/generate-adapter.mjs`, imported read-only; contract `translateSegment(handle, text, {maxNewTokens, stoppingCriteria}) -> {text, inputTokens, generatedTokens, endedWithEos, finishReason: 'eos'|'max_new_tokens'|'stopped', maxNewTokens}`, `loadDirection(...)` fails closed with `ADAPTER_ASSUMPTION_FAILED`). A job is complete only if every segment has `finishReason === 'eos'` and `endedWithEos === true`; otherwise `done{complete:false, outputs:[], reason}` with `TRUNCATED` (stops at the first truncated segment, partial text never leaves the worker), `DEADLINE`, `CANCELLED`, or `INCOMPLETE` (contradictory/unknown adapter result, or `stopped` with neither our deadline nor cancel flag). Supervisor: worker reason `TRUNCATED` -> `FAILED/TRUNCATED`, not a breaker failure (one pathological input must not open the circuit for everybody); coordinator -> `UNAVAILABLE/truncated`, never cached, identical calls run again (no negative caching). The default budget `min(512, 2n+16)` is applied by the adapter; `deadline-criteria.mjs` keeps an identical copy asserted equal by a test. `SPIKE_MAX_NEW_TOKENS` (test/bench only) forces a small integer budget. Tests: `test/run-job.test.mjs` (13, fake adapter), `test/truncation.test.mjs` (3, fake worker). Real-model truncation: section 6.9.

### 6.4 Client disconnect hook

The spec's `req.on('close')` is wrong. Node 24 docs (http): `IncomingMessage` `'close'`: "Emitted when the request has been completed." (History v16.0.0: "The close event is now emitted when the request has been completed and not when the underlying socket is closed."); `'aborted'` is deprecated since v17 ("Listen for `'close'` event instead"). `http.ServerResponse` `'close'`: "Indicates that the response is completed, or its underlying connection was terminated prematurely (before the response completion)." `response.writableFinished`: "Is `true` if all data has been flushed to the underlying system, immediately before the `'finish'` event is emitted." (`writableEnded` only says `end()` was called.) `request.socket`/`message.socket` is the underlying `net.Socket`.

Chosen hook (`bench/disconnect-hook.mjs`): `res.once('close', () => { if (!res.writableFinished) abort(); })`, removed explicitly when the handler has written its response. `test/disconnect.test.mjs` (8 tests, real sockets): (a) normal GET that waits for a fake translation: abort not fired, listener count back to its baseline after the response; a characterisation test shows `req` `'close'` fires BEFORE the response is finished on a normal GET (Node 24.0.1), i.e. the spec hook would abort healthy requests (also shown by a mutation run: swapping in the `req` hook fails 6 of 8); (b) client destroys the socket while waiting: abort fired once, that waiter settles `TIMEOUT/aborted`, another subscriber on the same key still gets `OK`, the job is not cancelled and one worker run served both; (b2) the only client leaves while RUNNING: abort once, cancel sent, next request OK; keep-alive requests, close after a complete response, and a POST with a body: no abort.

### 6.6 Model lock
