# Translation quality spike (Opus-MT vi<->en, local)

Status: **spike result, draft.** Written by an AI assistant (Claude Sonnet) on 2026-10-14. Not reviewed by a human. The reference translations are AI drafts, not human gold. Nothing here is an approved decision.

## Purpose

Measure, on a reproducible, synthetic fixture set for a software-licence management system, how good the local `Xenova/opus-mt-vi-en` and `Xenova/opus-mt-en-vi` models (q8, CPU, `@huggingface/transformers`) are as a "reference translation" of free-text fields (request justifications, approve/reject reasons, revoke and handover notes, renewal notes), and whether the planned safeguards help:

- per-sentence translation,
- placeholders `<xN>` for names, software, emails, URLs, codes, dates, amounts,
- a vi<->en glossary applied through placeholders,
- a placeholder gate (a segment with a missing, extra or duplicated placeholder keeps its original text),
- a token guard (over-limit segments are not translated).

This feeds plan step 0 and TR-AC-17 of the item (`../plan.md`, `../spec.md`). It does not touch product code.

Polarity gate trade-off (a detection heuristic, not a meaning guarantee). Two lexicons per language: narrow **trigger** cues decide what the source requires; the output is read with the triggers plus wider **satisfier** cues (synonyms) so valid paraphrases are not rejected. Compound cues are matched first and blanked out (`chưa được duyệt` and `has not been approved` are one reject cue), neutral compounds are blanked (`không gian`, `hàng không`, `not only`, a question-final `... không?`), protected spans other than glossary terms are blanked in both texts, and unaccented Vietnamese is read with folded cues (except ones that collide with common words). _False fallbacks:_ a correct paraphrase without a lexicon cue (`ủng hộ` for approve, `hết seat` for no seat) loses a translation that was fine. _Misses:_ the gate checks that a cue of the class is present, not that it is attached to the right clause; a cue the model adds elsewhere satisfies it, and a hallucinated negation in the output when the source has none is not detected at all. Wider satisfier lists mean fewer false fallbacks and more misses; the lists were fixed before the benchmark run and not tuned afterwards.

Reading the numbers (all one machine, synthetic data, AI references, keyword checks):

- **The safeguards trade coverage for safety.** In protected mode a third of vi-en fields and 17-35% of en-vi fields are returned untranslated, but among the fields that are shown, 1-3 of 33-70 fail an automatic keyword check (raw: 26-40 of 51-83). The chrF over translated fields (60-66) is not comparable to the all-field chrF (35-41): fallbacks count as the source text.
- **The placeholder gate is the largest source of fallbacks** (18/84 vi-en, 13/84 en-vi main fields; the 3.8.1 gate analysis counted 18/80 vi-en and 7/79 en-vi _segments_, a different unit, so only vi-en is directly comparable and it is the same). The 4.3.1 model damages placeholders at least as often as 3.8.1. A tolerant repair step is still unmeasured.
- **What the polarity fallbacks are** (read from run 1/final diagnostics, not adjudicated): on the main set 8 + 1 fields; most are real model errors the gate correctly stopped (`Đã duyệt` came out as "Browseed", `từ chối` was lost in the unaccented item, "ký duyệt" became "Sign the proposed browser"), the rest are lexicon limitations: `duyệt` meaning _review_ (vi-049, vi-067), `nếu không` meaning _otherwise_ (vi-039), `ủng hộ` for endorse (h-en-011), `cấp phép` / `rút lui` / `xóa bỏ` for revoke/refuse wordings, "voided" for revoked. The held-out sets, with new wordings, lose 10/54 and 8/51 fields to the polarity gate, i.e. **about 16-19% of all held-out fields fall back on wordings the lexicon was not written for** (several of those are real model errors, so this is an upper bound on false fallbacks, not a measured false-fallback rate). This is the false-fallback / miss trade-off, not a result about meaning.
- **`max_new_tokens` detection works**: the two mixed-language "Please approve giúp em …" items (vi-073, h-vi-046) make the model loop until the budget; without disabling `forced_eos_token_id` they would have been returned as complete translations.
- **Not caught by any gate** (examples from the final run): `licence` became `bằng lái` (driving licence) in en-040 and passed every keyword check; a 115-token vi sentence lost its second half and ended with EOS (ad-hoc test, not a fixture). A length-ratio check on output versus input tokens would address the second; not implemented, not measured.
- **Verbatim dates** make four old fixture checks fail by design (vi-039, vi-049 are fallbacks now; en-040 and en-050 are flagged with the `verbatim-date` note in `flags-4.3.1.json`).

## How to run

All commands run inside `spike/quality/`. Plain ESM, no dependencies of its own.

```
node --test                                   # unit tests, no model needed (3 real-model tests are skipped)
SPIKE_REAL=1 SPIKE_DEPS_DIR=<dir> node --test # also runs the real-model tests (adapter, model glue)
node fixtures/build.mjs                       # regenerate fixtures/*.json (main + held-out) from fixtures/src/*.mjs
node tools/freeze-431.mjs                     # record sha256 of lib/*.mjs and fixtures BEFORE a run; --check afterwards
SPIKE_DEPS_DIR=<4.3.1 project> node run-benchmark.mjs --direction vi-en --mode both --fixtures main,heldout --tag 4.3.1
SPIKE_DEPS_DIR=<4.3.1 project> node run-benchmark.mjs --direction en-vi --mode both --fixtures main,heldout --tag 4.3.1
node tools/flags-431.mjs                      # results/flags-4.3.1.json (translated fields with a failed automatic check)
node tools/summary-431.mjs                    # append / replace the 4.3.1 section of results/summary.md (baseline text untouched)
node summarize.mjs                            # (baseline) rebuild the 3.8.1 part of results/summary.md; keeps the 4.3.1 section
```

`run-benchmark.mjs` options: `--direction vi-en|en-vi|both` (default both), `--mode raw|protected|both` (default both), `--fixtures main|heldout|main,heldout` (default main), `--tag <label>` (files `results/<date>-<tag>-<set>-<direction>-<mode>.json`, summary.md untouched), `--warmup N` (default 2; first N fixtures, discarded), `--repetitions N` (default 3; per-item latency is the median of N timed runs), `--out <file>`, `--max-segment-tokens N` (default 128), `--limit N` (first N fixtures, smoke test), `--known-terms fixture|none` (default `fixture`, see limitations). `--max-tokens` and `--batch-size` no longer exist (batch size is always 1; the old 512 guard became the 128-token segment limit). ## Fixture design

- 84 items per direction. `vi-en.json`: Vietnamese source, English reference. `en-vi.json`: English source, Vietnamese reference. Items are not translations of each other one-to-one in every case, but most scenarios are mirrored.
- Synthetic only: invented people (Nguyen Van An, Tran Thi Bich, ...), invented company names, codes (`REQ-2026-0042`, `HD-2026-15`, `LIC-2026-0007-2`, `CC-0042`, `PO-2026-118`), e-mail addresses on `*.example` (enforced by a test).
- Fields: `id`, `source`, `reference`, `categories`, `protected` (exact strings that must survive unchanged), `mustContain` (list of any-of groups) and `mustNotContain` (substrings), both case-insensitive. Polarity categories get default checks: negation (`not`/`n't`/`no`/... or `khong`/`chua`/...), approve (`approv` and none of `reject`, `declin`, ...), reject (reject-like word and not "is/was/has been approved"), revoke (`revok*` or `thu hoi`). Glossary items add checks for the target term (for example `cancellation deadline`, `bàn giao`).
- Coverage per direction (counts include overlaps): negation 17-19, approve 9, reject 9-10, revoke 9-10, name 15-17, number 12-13, date 13-14, software 34, email 3, code 7-8, glossary 39-42, long 4, collision 3, mixed 3, plain 7-10, plus 4 unaccented items in vi-en.
- Long items (single sentence, no inner full stop): 314, 412, 480 and 605 tokens raw in vi-en (361, 469, 546, 687 once placeholders are inserted; the 546 and 687 ones exceed the 512 guard in protected mode, the 605 one also raw).
- Collision items literally contain `<x0>`, `<x1>`, `<x2>`.
- A test (`fixtures.test.mjs`) checks counts, uniqueness, that every protected string occurs in source and reference, and that **each reference passes its own checks**.
- **Reference caveat:** `referenceAuthor` is `"AI draft by Claude Sonnet — not reviewed by a human; Opus coordinator spot-check pending"`. chrF against these references measures similarity to one AI draft, not translation quality.
- `--known-terms fixture` (default) feeds each item's `protected` list to the protector as the "known terms" input, mirroring a product that knows person names and software names from its directory and catalogue. See limitations.

## Metric definitions

- **chrF:** character n-gram F-score, n = 1..6, beta = 2, whitespace removed, case-sensitive, code points, NFC-normalised, orders without n-grams skipped (sacreBLEU 2.x defaults). Corpus level sums n-gram statistics over all items before scoring; sentence level scores one pair. Cross-checked against sacreBLEU 2.6.0 (signature `nrefs:1|case:mixed|eff:yes|nc:6|nw:0|space:no|version:2.6.0`): corpus differences <= 0.004 and sentence differences <= 0.005 on all four result files, i.e. rounding only (the check NFC-normalises both sides first; 2 en-vi raw outputs and 0 others were not in NFC).
- **Protected terms preserved (%):** share of items (that have protected terms) whose output contains every protected string verbatim, case-sensitive.
- **Meaning checks passed (%):** share of items (that have checks) whose output satisfies all `mustContain` groups and no `mustNotContain`. These are keyword checks, so synonyms fail and garbled text can pass. A segment that fell back to the original text also fails the check (the output is in the wrong language), so see the next line.
- **Silent meaning failures:** items whose check failed **and** no segment fell back, i.e. a wrong or garbled translation that was shown without any warning. "Silent polarity failures" restricts this to negation/approve/reject/revoke items.
- **negation/approve/reject/revoke checks passed (%):** meaning checks over items with that category.
- **Segments fallen back (%):** segments that kept the original text (gate failure, guard, or model error) over all segments.
- **Latency:** per item, median of 3 timed runs of the whole pipeline (segmentation, protection, translation of all segments of the item, restore); p50 and p95 over the 84 items. Includes the 4 long items. **Load time:** `pipeline()` construction. **Peak RSS:** `process.resourceUsage().maxRSS` of the process after the runs.
- Greedy/beam decoding was deterministic: 0 items differed between repetitions in all four runs.

## Findings

1. **Padded batches corrupt shorter sentences.** Translating several sentences in one `pipe([...])` call made the shorter ones end with `!`, `!!` or `!!!` (reproduced in a 3-sentence probe, and in 2 of the 3 multi-sentence fixtures at batch size 8). The runner therefore uses batch size 1 (one segment per call). The spec's "batch the sentences" needs either equal-length bucketing, stripping a trailing `!` run that is not in the source, or batch size 1 plus concurrency.
2. **Protection fixes names, codes, amounts and dates; it does not fix fluency.** Protected-term preservation goes from 34% / 16% to 100% (with oracle known terms). chrF barely moves in vi-en (35.8 to 36.6) because 24% of segments fall back to the Vietnamese original, but it rises 12 points in en-vi.
3. **The model damages placeholders often enough to matter.** 18 of 80 segments (vi-en) lose the gate, mostly with 3 or more placeholders in the segment, and over half of the missing cases are visibly damaged tokens (`x0>`). A tolerant repair step (accept `x0>`, `<x0`, `[x0>` when exactly one expected id is missing and the damaged token is unambiguous) could recover many of them; not implemented, not measured, and it could mis-assign ids. Needs its own test before anyone relies on it.
4. **Long single sentences degenerate** (repetition in vi-en from about 190 tokens, truncation in en-vi at about 450+). The 512-token guard is not a quality limit; it is only the hard model limit. With placeholders added, segments are about 14-16% longer in tokens than raw text.
5. **Glossary through placeholders has side effects.** It fixes `Người duyệt chi`, `cancellation deadline`, `seat`, `Cost Center`, but bare `phòng` also means "room" (guarded so it is a department only before a capital/digit or at a clause end), and a placeholder cannot be inflected, so English forms are chosen by a small heuristic on the preceding word (`will be <x0>` gives `revoked`). Unaccented Vietnamese is still garbled by the model (vi-en unaccented meaning 33% protected, 0% raw), even when the glossary term is recognised.
6. **Output was in NFC except for 2 en-vi raw items**; compare after normalisation.

## Limitations

- **Synthetic data.** 84 invented items per direction in an English/Vietnamese register that one assistant produced; real user text (typos, slang, long free text, mixed scripts) is not represented.
- **AI references, no human gold.** chrF compares with one draft. The keyword checks are crude: they reject valid synonyms (`accepting`, `tán thành`) and accept garbled text. `mustContain`/`mustNotContain` were written by the same assistant that wrote the references.
- **Oracle known terms.** In `--known-terms fixture` mode the protector is handed the exact names/software of each item. Product reality is a directory plus catalogue lookup; unknown names get no protection. The regex-only ablation (74% / 63% preserved) shows the size of that gap. The 100% preservation figure must not be read as "the product preserves 100%".
- **chrF is not meaning.** A high score is compatible with a flipped negation; polarity checks cover only keyword presence.
- **Single machine, shared CPU.** One run on one Windows laptop, other Node sessions running; latency and RSS are indicative. RSS is process-wide peak after the runs.
- **Small samples per category** (3 emails, 3 collisions, 4 unaccented, 3 mixed, 4 long); percentages for those categories are anecdotes. Gate-failure statistics come from about 80 segments per direction.
- **Heuristics not validated:** the English form chooser for glossary verbs, the textual date localiser (`ngày 15 tháng 11` <-> `November 15`), the `phòng` guard, the abbreviation list in the segmenter (initials such as `A.` are not handled). Number formats (`1.500.000` vs `1,500,000`) are kept as written, not localised.
- **Not covered:** concurrency, cache, timeouts, memory with both models loaded, other model revisions, other languages, security review of placeholder handling beyond the collision rule, long-sentence comma splitting, placeholder repair.

Each module was written test-first; the first run of every test file failed before the implementation existed (module not found), then passed. ## Limitations added by the 4.3.1 phase

- **Keyword flags are not quality.** "Automatic flags" count failed `mustContain` / `mustNotContain` / protected-term checks; they miss fluent-looking errors (`licence` rendered as `bằng lái` passed) and flag valid synonyms (`tán thành`, `accepting`). `flags-4.3.1.json` is for adjudication by a person; nothing in this folder is human reviewed.
- **The polarity gate is a presence heuristic with a hand-written lexicon.** It cannot judge scope, hallucinated negations, or paraphrases outside the lexicon (see the trade-off paragraph). The lexicons were written before the runs and corrected only for the two bugs listed; they were not tuned on the results. The held-out polarity-fallback rate (16-19% of fields) is the figure to read, not the main-set rate.
- **The held-out sets are small** (54 and 51 items), written by the same assistant that wrote the main fixtures and the lexicons, with AI-draft references; they are "new wording", not "independent data".
- **Fallback is high by construction** (31-35% of fields in three of four sets). The placeholder gate and the polarity gate are conservative; whether that is acceptable is a product decision, and a placeholder repair step and a length-ratio check are untested ideas.
- **Truncation is only detected through `finishReason`.** A model that ends early with a natural EOS but drops half the content (observed once, ad-hoc) is not detected.
- **Known terms are an oracle** (unchanged); the 100% preservation figure only holds for terms the product can supply.
- **Latency** comes from one shared machine, default ORT threads, and varied by up to 1.8x between two identical-code runs; segment latency is per model call including tokenization.
- **Raw mode cannot translate inputs over 512 tokens** (the adapter refuses them), so raw does not reproduce the 3.8.1 behaviour of silently truncating them.
